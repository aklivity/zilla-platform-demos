# Use a fresh query ID each run to avoid replaying a cached Kafka result CROSS_QID="q-cross-$(date +%s | head -c8)" # Terminal A — standard stream (stays silent) curl -k -N -H "Authorization: Bearer $TOKEN_STD" \ "https://localhost:7143/results/$CROSS_QID" # Terminal B — enterprise query curl -k -X POST https://localhost:7143/queries \ -H "Content-Type: application/json" \ -H "Authorization: Bearer $TOKEN_ENT" \ -H "Idempotency-Key: $CROSS_QID" \ -d "{\"query_id\":\"$CROSS_QID\",\"question\":\"What is Zilla?\"}" # Terminal C — enterprise stream (receives answer) curl -k -N -H "Authorization: Bearer $TOKEN_ENT" \ "https://localhost:7143/results/$CROSS_QID" # Terminal A stays silent — sse-kafka tier filter blocked delivery
6
Tamper Test
Standard token claims enterprise tier in body — Zilla ignores it, stamps from JWT
▾
The request uses a standard token but includes "user_tier":"enterprise" in the JSON body. Zilla extracts tier exclusively from the JWT identity claim — the body field is ignored entirely.
{ "query_id": "q-tamper-1", "question": "What are Zilla Plus features?", "user_tier": "enterprise" ← Zilla ignores this }
Zilla stamped from JWT: user-tier: standard
Body field user_tier: enterprise was stripped and ignored.
RAG chain sees: roles=['standard'] — public + internal visibility only.
curl -k -X POST https://localhost:7143/queries \ -H "Content-Type: application/json" \ -H "Authorization: Bearer $TOKEN_STD" \ -H "Idempotency-Key: q-tamper-1" \ -d '{"query_id":"q-tamper-1","question":"What are Zilla Plus features?","user_tier":"enterprise"}' # → 204 but RAG chain log: roles=['standard'] ← JWT identity, not body
